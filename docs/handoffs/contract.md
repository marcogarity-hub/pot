Behaviour the fold and UI must match:
- **`expire` emits only `Expired(potId)`, not `Frozen`.** Treat Expired as state 4 (Frozen). The threshold path emits `Objected`, then `Frozen`, in the same tx.
- **The last `pay` emits `Paid`, then `Locked`, in the same tx.**
- **A swap refund has no `Refunded` event.** It appears only as `SeatSwapped.refunded`, which is the share if the leaver had paid and 0 otherwise. In that case mark the leaver refunded and inactive.
- **`paymentsCount` only goes down on a swap-out of a paid seat** (by exactly 1). It never goes down on `refund`, so in Frozen or Funding-after-deadline it does not mean "money still in".
- `hasPaid` is never cleared. An objector can still refund in Frozen.
- `getPot` returns a named tuple: organizer, total, share, deadline, threshold, objectionWindow, requestWindow, lockedAt, state (uint8 on the wire), paymentsCount, objectionsCount, receiptHash, releaseEligibleAt, members. If `organizer == address(0)`, the pot doesn't exist.
- Revert order, so the API can map errors:
  - pay: WrongState, DeadlinePassed, NotMember, AlreadyPaid, WrongAmount.
  - refund: WrongState, DeadlineNotPassed, NotRefundable, AlreadyRefunded.
  - swapSeat: NotOrganizer, WrongState, DeadlinePassed, NotMember, ZeroAddress, DuplicateMember, FormerMember.
  - requestRelease: NotOrganizer, WrongState.
  - object: WrongState, WindowClosed, NotMember, AlreadyObjected.
  - finalizeRelease: WrongState, WindowOpen.
  - expire: WrongState, RequestWindowOpen.
  - createPot: InvalidParams (including `share * n` overflow), ZeroAddress, DuplicateMember.
  - A wallet whose receiver rejects value gets `TransferFailed`.
- Payouts and refunds are **push** transfers. Member and organizer wallets must accept native USDC. Circle developer-controlled EOAs do.
- `POT_ADDRESS` is typed `` `0x${string}` `` but is `undefined` until `NEXT_PUBLIC_POT_ADDRESS` is set, so check it before use. `POT_DEPLOY_BLOCK` reads the server-only `POT_DEPLOY_BLOCK`, so it is `0n` in browser bundles.
- `arcTestnet` uses explorer `https://explorer.testnet.arc.io` (Arc docs; it matches viem 2.57.19's built-in definition).

### Blockers / decisions for Marco
1. **A contract organizer that rejects payment can strand a pot.** This came from the Codex review and is the same as item 14 of the earlier spec review; no amendment covered it.
   - If the organizer can't receive native USDC, `finalizeRelease` reverts with `TransferFailed` and the pot stays PayoutRequested.
   - After the objection window closes, nothing can move the money: `object` is closed, `expire` needs Locked, and `refund` needs Funding or Frozen.
   - While the window is open, members can still object and freeze the pot.
   - It can't happen in the app, because organizers are Circle EOAs (A1). It can happen if someone calls the contract directly from a contract organizer.
   - `test_RejectingOrganizer_FinalizeReverts_KnownGap` pins the current behaviour.
   - Every fix needs an interface change, which this lane is not allowed to make. Options:
     - (a) A pull-payment `withdraw()` for the organizer.
     - (b) Let `expire` (or a new function) move PayoutRequested to Frozen after `releaseEligibleAt + requestWindow`.
     - (c) Accept the gap and document it in the README.
   - Recommendation: (c) for the hackathon, (b) afterwards.
2. **`requestRelease` stays allowed after `lockedAt + requestWindow` until someone actually calls `expire`** (ruling R5). The plan and A4 don't say otherwise. It's harmless, because the objection window still applies, but if you want a hard cutoff that's a new revert path.
3. **There is no upper bound on `deadline`.** A far-future deadline holds members' payments in a pot that never fills; their only exit is the organizer swapping them out. Either add a cap in the contract (for example 365 days, reverting `InvalidParams`) or have Lane 2/UI bound it. Your call.
4. **The same push-transfer issue affects swaps.** A paid leaver that rejects value blocks `swapSeat` for that seat (`TransferFailed`). This doesn't apply to EOA wallets.
